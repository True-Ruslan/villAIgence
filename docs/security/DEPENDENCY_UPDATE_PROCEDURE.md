# Controlled Dependency Update Procedure

This procedure is mandatory for changes to Gradle, build plugins, repositories, dependencies or GitHub Actions used by VillAIgence.

## Protected inputs

The following files are security-sensitive build inputs:

- `gradle/wrapper/gradle-wrapper.properties`;
- `gradle/wrapper/gradle-wrapper.jar`;
- `gradle/verification-metadata.xml`;
- `gradle.properties`;
- `settings.gradle`;
- root and subproject `build.gradle` files;
- `buildSrc/**`;
- `common/gradle.lockfile`;
- `fabric/gradle.lockfile`;
- `neoforge/gradle.lockfile`;
- `.github/workflows/**`.

## Dependency or plugin update

1. Change only explicit versions or repository rules required by the update.
2. Do not introduce dynamic versions, snapshots or changing modules unless a separate security review explicitly approves them.
3. Confirm the release and checksum from the dependency or tool owner's official source.
4. Run the **Supply-chain metadata generation** workflow on the update branch.
5. Download the `villaigence-supply-chain-metadata` artifact.
6. Inspect every diff in:
   - `gradle/verification-metadata.xml`;
   - `common/gradle.lockfile`;
   - `fabric/gradle.lockfile`;
   - `neoforge/gradle.lockfile`;
   - the generated dependency manifest.
7. Reject unexplained new repositories, groups, artifacts, classifiers or version changes.
8. Commit the generated verification metadata and lockfiles exactly as produced by Gradle. Do not hand-edit checksums.
9. Run all required workflows:
   - VillAIgence CI;
   - Java Pull Request CI with Gradle;
   - Supply-chain metadata generation;
   - VillAIgence GitHub Release dry-run.
10. Merge only when Fabric, NeoForge, tests, wrapper validation, dependency verification and release packaging all succeed.

## Gradle wrapper update

1. Select an explicit stable Gradle release.
2. Obtain the binary distribution SHA-256 from the official Gradle checksum page.
3. Update `distributionUrl` and `distributionSha256Sum` together.
4. Regenerate the wrapper only through the official Gradle wrapper task.
5. Review the wrapper JAR change separately.
6. Confirm `validate-wrappers: true` remains enabled in every workflow that invokes Gradle through an external setup action.
7. Complete the full dependency/plugin update procedure above.

## GitHub Action update

1. Select a documented upstream release.
2. Resolve the release tag to its full 40-character commit SHA in the action's official repository.
3. Use the immutable SHA in `uses:` and retain the human-readable version as a trailing comment.
4. Never merge a mutable tag such as `@v4`, `@main` or `@latest`.
5. Confirm the repository-level `SupplyChainPolicyTest` accepts every workflow.
6. Run every workflow affected by the action.

## Repository update

Every non-central Maven repository must use the narrowest practical `exclusiveContent` or `content` filter.

A repository may be added only when:

- the required artifact is not available from an already approved repository;
- its exact group is documented;
- the repository is restricted to that group or smaller scope;
- verification metadata and lockfiles record the resolved artifact;
- Fabric and NeoForge builds remain reproducible.

## Verification metadata rules

- SHA-256 is the minimum accepted checksum algorithm.
- Existing checksums must not be deleted merely to make a build pass.
- A checksum change for the same immutable coordinate is a security event and requires investigation.
- Verification metadata generation is a controlled maintenance action, not part of a normal release.
- Normal CI and release builds consume committed metadata and must not regenerate it.

## Lockfile rules

- Lockfiles are committed for `common`, `fabric` and `neoforge`.
- Lockfile changes must correspond to intentional dependency changes.
- Normal CI must consume committed locks.
- `--write-locks` is allowed only during the controlled metadata-generation workflow or an equivalent reviewed local maintenance run.

## Release evidence

Every GitHub release must retain:

- the distributable VillAIgence JAR;
- its SHA-256 checksum;
- the deterministic sorted dependency manifest generated by `:dependencyManifest`.

The dependency manifest is timestamp-free so equivalent dependency graphs produce reviewable output.

## Emergency rule

A broken dependency must not be bypassed by disabling verification, deleting metadata, using a dynamic version, broadening repositories without filters or replacing immutable action SHAs with mutable tags.

Emergency fixes follow the same workflow with a smaller scope and an explicit incident note.
