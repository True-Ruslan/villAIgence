## Root cause

`0.3.1` added a query-relevant candidate lane before the existing final Memory 2.0 rank-to-6 step, but two gaps remained.

### Gap 1 — participant matching was counted twice

Exact NPC/player eligibility was already enforced before bounded candidate allocation. Final ranking nevertheless treated participant matching as a positive relevance dimension for every eligible dialogue.

With a useful current query:

```text
old targeted dialogue with one lexical overlap
  participant relevance = 100
  lexical relevance     = 50
  combined relevance    = 75
  old recency           = 0

fresh unrelated eligible dialogue
  participant relevance = 100
  lexical relevance     = 0
  combined relevance    = 50
  fresh recency         ≈ high
```

Because relevance contributes 40% and recency 20% to the final score, sufficiently fresh unrelated dialogue could still outrank an older one-token lexical match. Candidate selection therefore succeeded while final rank-to-6 could still starve the target.

The PR #165 regression used a source fixture with at least two useful lexical overlaps (`личный` + `маркер`), which yielded maximum lexical relevance and did not exercise this weaker-match boundary.

### Gap 2 — explicit referential recall can have zero lexical overlap

The exact archived raw text of Muammer's original marker event was not available to this development session. Therefore a second patch must not assume that the retained source contains a useful word from the later question.

A player can persist an opaque identifier using wording such as:

```text
Запомни amber-pine-314.
```

and later ask:

```text
Муаммер, назови личный маркер, который я ранее сообщил именно тебе.
```

The exact owner-local event can be the intended referent while lexical relevance is zero. Pure token overlap cannot safely recover that class of request.

The corrective design therefore stays deterministic and server-owned:

```text
already eligible PLAYER_TOLD DIALOGUE
+ explicit marker/code/token recall intent in current query
+ explicit storage cue in original player text
+ bounded machine-like opaque identifier in original player text
→ referential marker recall score
```

It is deliberately not embeddings, semantic/vector search, provider-assisted retrieval, a larger window, or a new persistence model.

## Final runtime policy

Head `9148039e938bef8e9ee5eca87d089fed7f31c5a7` adds the missing source-side storage cue requirement.

The zero-overlap fallback now requires all of:

```text
current query has explicit marker/code/token recall intent
AND event is DIALOGUE / PLAYER_TOLD
AND event already passed exact NPC/player eligibility
AND original player text contains an explicit storage cue
    (Russian запомн*/сохран* or English remember/save/keep)
AND original player text contains a bounded machine-like opaque identifier
```

If structured `DialogueExchange` exists, only `playerMessage` is inspected. Historical events without structured dialogue use their bounded summary fallback.

The score is used consistently in both:

- the existing max-8 query-relevant lane inside the unchanged max-32 candidate set;
- the existing final max-6 ranking.

When no explicit recall intent exists, legacy retrieval behavior remains unchanged.
