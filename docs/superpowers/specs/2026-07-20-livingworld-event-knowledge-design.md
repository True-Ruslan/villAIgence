# LivingWorld Event / Knowledge Foundation Design

## Goal

Give LivingWorld NPCs bounded awareness of recent, server-verified local events without turning every event into global NPC knowledge and without trusting arbitrary player/LLM text as factual world state.

## Decision

Use a small world-local event journal as the factual source layer. Events are immutable, server-generated records with provenance, dimension, position and game time. The current milestone exposes only events an NPC could plausibly observe locally. Persistent beliefs, player claims, rumors and NPC-to-NPC propagation are explicitly separate future layers.

## Data model

`WorldEvent` contains:

- stable event id;
- event type;
- deterministic server-generated description;
- provenance (`SYSTEM_OBSERVED` initially);
- dimension id;
- block position;
- game time;
- optional actor UUID;
- optional subject UUID.

Descriptions are generated by code, never accepted verbatim from the LLM.

## Storage

A bounded `WorldEventStore` lives at `<world>/livingworld/events.json`.

Defaults:

- enabled: true;
- retain at most 512 events;
- retain at most 3 Minecraft days (72,000 ticks) when queried/compacted;
- context radius: 32 blocks;
- inject at most 8 recent events per snapshot.

Writes use temp-file + atomic replace where supported, matching the persistent conversation-memory pattern. I/O failures are fail-open: AI conversation continues without event context.

## First event source

Successful whitelisted LivingWorld NPC actions emit deterministic events after the action is revalidated on the Minecraft server thread. Examples: follow, stay, move freely, go home, open trade, wear/remove armor.

This is intentionally narrow. It proves the event pipeline and provides useful recent context without inventing broad gameplay hooks.

## Context flow

1. Minecraft server thread captures the normal `LivingWorldContextSnapshot`.
2. During capture, query recent events in the villager's dimension and radius.
3. Add bounded lines marked as `Observed recent local event` to factual context.
4. Snapshot remains immutable before async LLM work.

An NPC therefore sees only recent nearby server-verified events. The event journal is not presented as omniscient memory.

## Security and truth boundary

- LLM output cannot create arbitrary factual events directly.
- Player statements are not stored as observed facts.
- Event descriptions are deterministic code-generated strings.
- Event query is bounded by dimension, distance, age and count.
- Event storage cannot execute actions.
- Existing safe-action whitelist remains authoritative.

## Failure behavior

- Missing/corrupt event store: log warning and continue with no events.
- Failed write: action result remains valid; event persistence failure does not roll back gameplay.
- Unknown event type on load: ignore safely where possible or reset invalid file data without crashing the server.

## Testing

- persistence/reload;
- max-event bound;
- age/radius/dimension filtering;
- newest-first deterministic ordering;
- fail-open bridge behavior;
- formatter produces deterministic event text;
- full Fabric/NeoForge CI before merge.

## Explicitly out of scope

- rumors;
- player claims as facts;
- semantic/vector memory;
- NPC-to-NPC propagation;
- confidence decay;
- event-driven autonomous action planning;
- broad hooks for combat/death/building/quests.

Those build on this source-of-truth event layer in later PRs.
