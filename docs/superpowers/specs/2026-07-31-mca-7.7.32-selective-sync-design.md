# MCA 7.7.32 Selective Synchronization Design

## Status

Approved design for selectively integrating relevant upstream MCA `1.21.1` changes into VillAIgence without weakening VillAIgence identity, persistence, AI authority, security or supply-chain guarantees.

## Problem statement

VillAIgence began as an MCA fork but now contains hundreds of independent commits implementing persistent NPC memory, semantic knowledge, relationships, events, voice identity, server-authoritative AI actions, immutable context capture, bounded provider networking and repository security policy.

Upstream MCA continued to evolve after the common `7.7.22` base. Its newer `1.21.1` line includes high-value corrections and features, notably:

- tombstone item data-loss correction;
- UUID-preserving villager ↔ zombie conversion;
- occupied-bed POI correctness;
- water, collision and ladder navigation improvements;
- pathfinding load distribution;
- graveyard/mourning behavior;
- ChatAI Context Editor;
- client rendering and EMF support;
- Skin Library fixes and other compatibility work.

A whole-branch merge would also overwrite or conflict with VillAIgence-specific AI, security, persistence and navigation work. A sequential cherry-pick would preserve upstream's mixed/intermediate commit structure and make reviews, rollback and defect isolation unreliable.

## Goals

1. Import upstream corrections that materially improve data integrity, NPC identity, navigation and compatible MCA behavior.
2. Preserve VillAIgence as the authoritative architecture for AI, memory, relationships, voice, events and provider security.
3. Make every imported subsystem independently reviewable, testable, revertible and releaseable.
4. Preserve world compatibility and support rollback to the last known-good release.
5. Keep exact upstream provenance for every accepted change.
6. Separate core correctness from optional client, service and cosmetic changes.
7. Establish a repeatable upstream-adoption process for later MCA releases.

## Non-goals

This synchronization does not:

- make VillAIgence identical to upstream MCA;
- merge the complete upstream branch;
- import upstream workflows or scripts;
- replace VillAIgence `OpenAIChatAI` transport or parsing;
- start legacy `memory.json` migration;
- implement milestone `0.3` personality profiles;
- classify generated biographies as facts;
- add arbitrary LLM command execution;
- promise compatibility with every third-party mod mentioned upstream;
- combine all accepted changes into one release.

## Chosen integration model

### Rejected: whole-branch merge

A whole-branch merge would combine unrelated changes across AI, entity lifecycle, navigation, client rendering, networking, resources, scripts and CI. It would make it difficult to prove that existing security and persistence guarantees survived.

### Rejected: blind chronological cherry-pick

The 53 upstream commits contain release aggregation, merge commits, intermediate implementations and large mixed patches. Several later commits correct earlier implementations. Chronological cherry-picking would reproduce upstream's development history instead of porting its final intended behavior.

### Accepted: subsystem final-state patch port

For each subsystem:

```text
record upstream final target SHA
→ inspect all contributing commits and final files
→ define VillAIgence invariants
→ write failing regression tests
→ manually port the minimal final behavior
→ reconcile with existing VillAIgence code
→ run common/Fabric/NeoForge/security checks
→ run subsystem-specific real-server acceptance
→ merge one focused PR
→ update adoption evidence
```

The original upstream SHAs remain in the PR description for attribution and future re-audit.

## Architecture boundaries

### 1. NPC identity boundary

Persistent VillAIgence state is keyed by NPC UUID. Conversion between `VillagerEntityMCA` and `ZombieVillagerEntityMCA` must preserve one logical character identity.

Affected external world-local files:

```text
<world>/livingworld/memory.json
<world>/livingworld/memory2.json
<world>/livingworld/semantic-memory.json
<world>/livingworld/events.json
<world>/livingworld/relationships.json
<world>/livingworld/voices.json
```

The conversion implementation must preserve the UUID before registering the new entity, avoid duplicate live entities, and preserve relevant MCA NBT/inventory/equipment state. External VillAIgence records are not copied or migrated during conversion; they remain valid because the key remains unchanged.

### 2. AI authority and transport boundary

VillAIgence remains authoritative for:

- provider endpoint normalization and credential binding;
- authenticated redirect denial;
- response byte limits and total body deadlines;
- safe `content:null` and malformed response handling;
- bounded retries without duplicate side effects;
- structured action and relationship proposal parsing;
- immutable snapshot use for asynchronous AI work;
- diagnostics that omit secrets, prompts and transcripts.

Upstream `OpenAIChatAI.java` may not replace any of these mechanisms. Only narrowly reviewed context-composition behavior may be adapted.

### 3. Factual context boundary

VillAIgence prompt layers remain semantically distinct:

```text
worldFacts               authoritative current server observations
memoryContext            episodic recalled events
semanticMemoryContext    typed FACT/BELIEF memory with provenance
operatorAuthoredContext  server-authored setting/character lore
```

`operatorAuthoredContext` is introduced only for the Context Editor train. It is not `SYSTEM_OBSERVED`, is not automatically persisted to semantic memory, and cannot override a contradictory current `worldFacts` observation.

### 4. Navigation boundary

VillAIgence already has a bounded progress watchdog that recomputes a stale path after sustained lack of movement while preserving `WALK_TARGET`. Upstream adds complementary capabilities:

- water-aware start/surface logic;
- climbable graph nodes and controlled ladder movement;
- ladder exit and oscillation fixes;
- deterministic staggering of expensive path checks;
- collision/door corrections.

The final design combines these behaviors. Upstream scheduling must not remove the progress watchdog. Upstream fixed-size clearance must not replace actual entity clearance unless comparative tests prove it is correct for adults, children and altered dimensions.

### 5. Persistence boundary

New persistence must be:

- world-local;
- schema-versioned;
- explicit and inspectable;
- atomically replaced;
- fail-soft on malformed auxiliary data;
- compatible with world backup/restore;
- additive unless a dedicated migration is designed.

The Context Editor's world scope is therefore stored under `<world>/livingworld/`, not in global MCA config.

### 6. Security and supply-chain boundary

The following remain controlled by VillAIgence and are excluded from upstream replacement:

```text
.github/workflows/**
scripts/**
gradle/wrapper/**
gradle/verification-metadata.xml
**/gradle.lockfile
docs/security/APPROVED_SCRIPT_INVENTORY.json
```

Any later change to these paths requires a dedicated security review and exact-head CI evidence.

## Work-package architecture

### S0 — Manifest and guardrails

Documentation-only package establishing audit SHAs, commit classifications, exclusions, release allocation and acceptance gates. No runtime behavior.

### S1 — Tombstone data integrity

Port the upstream correction from entity-data component use to block-entity-data serialization. Add a compatibility reader for previously produced items where safe. Prove block → item → block → restart round trips preserve stored NPC data.

### S2 — UUID-preserving conversion

Implement controlled entity replacement with preserved UUID and MCA conversion hooks. Add automated invariants and a real-server fixture containing all six VillAIgence persistence domains before infection and curing.

### S3 — HOME POI correctness

Claim only valid unoccupied beds, avoid double claims, safely reclaim the same home and preserve dimension-aware HOME memory.

### S4 — Water and collision navigation

Port water-tag-aware start/surface behavior, remove redundant door goal if the brain owns door handling, and reconcile collision checking with actual entity shape. This package establishes the navigation base for ladders.

### S5 — Ladder/climbable navigation

Port final climbable graph and motion behavior, including ascent, descent, floor entry/exit and oscillation corrections. Support the generic `BlockTags.CLIMBABLE` contract while preserving special ladder anchoring.

### S6 — Scheduling and progress integration

Replace shared task cooldown behavior with deterministic per-entity staggering while retaining the existing per-NPC progress tracker. Demonstrate absence of synchronized pathfinding bursts and unbounded recompute loops.

### S7/S8 — Later server/gameplay packages

Graveyard/mourning and isolated gameplay compatibility are deliberately separated from the first core correctness release. Each requires its own reproduction and acceptance matrix.

### S9 — Operator-authored lore foundation

Create world-local persistence and immutable snapshot integration without UI. Proposed schema:

```json
{
  "version": 1,
  "world": "",
  "villagers": {},
  "players": {},
  "villages": {}
}
```

Village keys must include dimension and stable village ID. Writes are atomic; malformed data fails open with backup/recovery behavior consistent with existing LivingWorld stores.

### S10 — Context Editor UI/networking

Adapt upstream's four scopes (`VILLAGER`, `PLAYER`, `VILLAGE`, `WORLD`) and stable target identifiers. The server validates permissions, dimensions, UUIDs, village IDs, length and stale targets. The client never decides authority.

### S11 — Generated personality profile

Explicitly outside synchronization. Generated biography, habits, preferences, goals and beliefs require deterministic persistent identity design in milestone `0.3`.

### S12–S15 — Optional client/compatibility trains

Destiny, Skin Library, EMF/rendering and gifts are isolated so their client or external-service regressions cannot force rollback of identity/data-integrity fixes.

## Release design

### Core correctness release

The first implementation train contains S1–S6. Its release number must be chosen after the security acceptance release sequence is reconciled. The previously suggested `0.1.16` is no longer assumed because PR #68 already reserves the expected next release for security acceptance tooling.

Release criteria:

- all common/Fabric/NeoForge/security checks green;
- tombstone round trip proven;
- infection/cure UUID round trip proven;
- six VillAIgence persistence files remain linked to the same NPC;
- bed POI correctness proven;
- water/ladder navigation scenarios pass;
- pathfinding performance gate passes;
- rollback JAR and world backup retained.

### Operator context release

S9–S10 ship only after core correctness stabilizes. `operator-lore.json` is included in backup/restart evidence. No generated profiles are included.

### Optional client release

S12–S15 may be split further and must not be required to consume the core server fixes.

## Testing strategy

### Automated layers

1. Pure unit tests for codecs, scheduling, progress tracking and identifier validation.
2. Common module tests for entity conversion helpers, persistence and prompt formatting.
3. Fabric build and package validation.
4. NeoForge compile/build compatibility.
5. Repository security policy, dependency verification and script inventory.
6. Dedicated-server classloading checks for client-only additions.

### Real-server layers

1. Snapshot a known-good world and exact JAR hash.
2. Run focused feature scenarios.
3. Capture sanitized logs and exact persistent-file hashes.
4. Restart and repeat assertions.
5. Verify Text, STT, Chat, Memory 2.0 and TTS smoke paths.
6. Reinstall rollback JAR against a copy of the post-test world and verify compatibility.

### Performance layer

Navigation changes are tested with controlled populations of 10, 50 and 100 NPCs. Record path checks, recomputes, simultaneous checks and tick latency. The core train is blocked if p95 tick duration regresses by more than 10% against the same-world baseline or if path checks form synchronized bursts.

## Error handling

- Conversion aborts without discarding the source if target entity creation fails.
- New entity registration must not leave two live entities with the same UUID.
- Auxiliary lore persistence failure logs a bounded diagnostic and leaves authoritative world state untouched.
- Invalid or stale editor updates are ignored or rejected without retargeting to a nearby entity.
- Navigation failures preserve intent where safe and use bounded recomputation.
- Provider failure behavior is unchanged by this synchronization.
- Client compatibility failures remain isolated from dedicated server startup.

## Rollback design

Known live-validated baseline:

```text
VillAIgence release: 0.1.15+1.21.1
JAR SHA-256: af142be94885541bb4840d0effff73627afe3f0e245dec8307ed665701cc94fb
```

PR #68 adds tooling after that release but does not invalidate it as the last live-validated production/security checkpoint.

Rollback rules:

1. Preserve a full world backup before each release candidate.
2. Keep persistence changes additive in the core train.
3. Do not delete or rewrite unknown fields.
4. Verify post-conversion worlds can load with the rollback JAR on a copied world.
5. Keep each subsystem PR independently revertible.
6. Feature-gate operator lore/context UI until live validation completes.
7. Never require deletion of Memory 2.0 files to roll back.

## Decision summary

The synchronization will proceed as a governed adoption program rather than a fork update. Core data integrity and identity are first, navigation second, operator context third, and optional client/service features last. VillAIgence architecture remains authoritative wherever upstream behavior conflicts with persistent identity, factual provenance, provider security or supply-chain controls.
