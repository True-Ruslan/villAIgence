# 0.3.1 Installed-Acceptance Reconciliation Design

## Goal

Reconcile VillAIgence's canonical project handoff with the already-published `0.3.1+1.21.1` corrective release while preserving the explicit distinction between automated/exact-release evidence and real installed acceptance.

## Current evidence boundary

- `0.3.1+1.21.1` is already published from commit `bc7c68ac2f3a4f761aa3b03a2f5c1fe1201745ab`.
- Official Fabric JAR SHA-256 is `f7f40b920c6f72a0e9af864795f48a0f90479db42a145081f43923b71a95e29f`.
- PR #165 fixed `VAI-PCM-MULTI-001` through deterministic query-aware Memory 2.0 retrieval while preserving the existing 32-candidate / 6-result bounds and NPC/player isolation.
- Release, CI, security, production acceptance, persistence recovery, GameTests, supported-loader builds and Production Soak are automated evidence only.
- `VAI-PCM-MULTI-001` is not installed PASS until the official 0.3.1 JAR is installed on the private test server and the crowded-history recall scenario is rerun against those exact bytes.
- `VAI-M2-INST-005` and `VAI-CONCUR-004` remain explicitly NOT TESTED/deferred.

## Design

### 1. Canonical handoff reconciliation

Update `docs/PROJECT_STATE.md` and `docs/ROADMAP.md` so their executive state reflects reality:

- latest official release: `0.3.1+1.21.1`;
- release commit: `bc7c68ac2f3a4f761aa3b03a2f5c1fe1201745ab`;
- `0.3.0` installed acceptance found one required recall defect;
- PR #165 corrected the defect and PR #166 published the patch;
- next step is installed 0.3.1 acceptance, not another release request and not 0.4 feature expansion.

The historical 0.3 capability/convergence sections remain intact. Reconciliation changes current status, immediate sequence and NEXT only.

### 2. Dedicated 0.3.1 installed ledger

Create `docs/livingworld/VALIDATION_0.3.1_CLEAN_WORLD_INSTALLED.md` as the canonical operator record for the corrective patch.

The file starts in an honest pending state. It records:

- exact tag, release commit, artifact filename and SHA-256;
- why only the affected installed boundary must be rerun;
- required installation identity checks;
- a targeted `VAI-PCM-MULTI-001` procedure using two NPCs, exact per-NPC markers and more than 32 newer eligible events for the affected NPC;
- explicit cross-NPC isolation assertions;
- restart sanity after the successful recall;
- PASS/FAIL recording rules;
- unchanged deferrals for `VAI-M2-INST-005` and `VAI-CONCUR-004`.

No result is pre-filled as PASS.

### 3. Policy regression test

Add `CurrentReleaseHandoffPolicyTest` before changing the docs. The test fails against the current branch because the canonical docs still identify 0.2/0.3.0 release-request state.

The policy asserts that:

- `PROJECT_STATE.md` names `0.3.1+1.21.1` and the exact release commit;
- `PROJECT_STATE.md` names installed 0.3.1 acceptance as NEXT and does not claim `VAI-PCM-MULTI-001` PASS;
- `ROADMAP.md` names installed 0.3.1 acceptance before 0.4;
- the dedicated validation ledger exists and contains exact release identity, `PENDING`, `VAI-PCM-MULTI-001`, the JAR SHA-256, and both unchanged deferrals.

This provides a deterministic RED→GREEN proof for the reconciliation contract.

## Non-goals

- no runtime production code changes;
- no persistence/config/provider schema changes;
- no migration/backfill;
- no release tag or artifact mutation;
- no claim that installed acceptance has passed;
- no start of 0.4 work before installed evidence exists;
- no attempt to automate away the real-client boundary by relabeling CI as installed evidence.

## Delivery

Use a dedicated branch from `bc7c68ac2f3a4f761aa3b03a2f5c1fe1201745ab`.

1. Commit this design and implementation plan.
2. Add the policy test only and open a draft PR to obtain GitHub Actions RED evidence.
3. Update the two canonical docs and add the 0.3.1 validation ledger.
4. Re-run the same policy/full selected CI until GREEN.
5. Review the exact branch diff and keep runtime/config/persistence/release-identity changes at zero.
6. Mark the PR ready and merge only after required checks are green.

Installed acceptance remains a separate operator action after merge; the repository must continue to say PENDING until the exact release JAR is actually exercised on the private server.
