# VillAIgence 0.2.0

Vill-AI-gence — Giving villagers a mind of their own.

This release begins the 0.2 Memory 2.0 line and promotes the persistent-dialogue clean cutover completed after `0.1.26+1.21.1`.

## Breaking pre-1.0 data boundary

`0.2.0` intentionally does **not** migrate the experimental pre-0.2 `<world>/livingworld/memory.json` conversation store.

Supported rollout for this development release is a clean LivingWorld state. The old raw conversation store is no longer opened, imported or recovered by the current runtime.

Do not point this candidate at the only copy of a valuable world. Use a dedicated test world or an offline copy and retain backups before validation.

## Memory 2.0 dialogue cutover

Persistent dialogue now uses one canonical path:

```text
successful text/voice turn
→ ChatAI post-success boundary
→ Memory2DialogueLifecycle
→ structured DIALOGUE MemoryEvent
→ memory2.json
```

Prompt history reads the structured `DialogueExchange(playerMessage, npcReply)` payload only. Human-readable episodic summaries are not parsed back into prompt roles.

Retrieval is isolated by exact NPC and player participants and filters eligible DIALOGUE events before applying result limits, so newer non-dialogue events cannot starve recent conversation history merely by occupying the generic event limit.

The old `ConversationMemoryStore` / `MemoryMessage` runtime path and `memory.json` recovery case are removed. `PersistentChatMemory` remains only as a no-storage compatibility adapter for the inherited AI call surface and does not perform a second persistent write.

## Current persistence boundary

The current auxiliary corruption/recovery matrix contains five stores:

```text
memory2.json
semantic-memory.json
relationships.json
voices.json
operator-lore.json
```

`events.json` remains authoritative factual event history with its own validation path.

Release recovery remains version-aware so immutable historical releases such as `0.1.26` continue to validate their own older persistence contract instead of being forced onto the current five-store model.

## Automated release assurance

The exact release-request candidate must pass:

- repository security and supply-chain policy;
- common/unit and deterministic mock-provider tests;
- required Fabric server GameTests;
- Fabric and NeoForge builds;
- exact production Fabric startup, controlled stop/save and same-world restart;
- current five-case destructive persistence-recovery matrix;
- real Simple Voice Chat transport evidence;
- distributable package smoke;
- byte-for-byte identity between the production-accepted and packaged JAR.

The release workflow uses no paid provider and no repository secret for deterministic acceptance scenarios.

The operator initially reported INST-006 and INST-007 as FAIL because the spoken seed `silver-fox-482` was transcribed by STT as `SilverFox482`. Root-cause review showed that this was an invalid test oracle: physical STT does not promise exact punctuation/case fidelity, while Memory 2.0 correctly persisted the accepted transcript and the NPC reproduced that same recognized content after restart.

Recorded non-blocking STT quality observation:

```text

```

This is not memory corruption or restart loss. Future physical-voice memory acceptance starts at the accepted STT transcript boundary; punctuation/hyphen/capitalization normalization is acceptable when the unique intended content remains recognizable.
