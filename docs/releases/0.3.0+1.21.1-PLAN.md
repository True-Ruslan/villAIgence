## Explicit non-scope

The candidate does not add or promise:

- autonomous high-frequency/per-tick LLM agents;
- graph-neighborhood enumeration, ranking or fallback target selection;
- open-ended provider-authored social mutations;
- autonomous visible NPC↔NPC LLM conversations;
- factions, politics or settlement-wide truth authority;
- 0.4 knowledge-ecosystem expansion beyond the already-merged bounded primitives;
- a migration/backfill system for experimental pre-1.0 test-server state.

## Automated acceptance matrix

Before an exact candidate may be requested, one frozen release-prep head must pass:

1. repository security policy;
2. complete VillAIgence CI;
3. common/unit + deterministic mock-provider tests;
4. required Fabric server GameTests;
5. Fabric + NeoForge supported loader builds;
6. exact production server startup, controlled stop/save and same-world restart;
7. current six-store destructive persistence recovery matrix;
8. production package verification;
9. Production Soak with constrained concurrency and repeated restart cycles;
10. full GitHub Release dry-run with `github-release` publication skipped;
11. independent base→head review with P0/P1/P2 = 0 and no unresolved review threads.

The convergence validator additionally checks that:

- the candidate identity is newer than the immutable previous release and has the current Minecraft suffix;
- every actual post-release `feat:` PR is represented exactly in the capability inventory;
- every capability PR is traceable from root `[Unreleased]`;
- world-store/recovery-store lists match the production acceptance code;
- the current manual/deferred boundary is explicit;
- a release request, if later supplied, exactly matches `0.3.0+1.21.1`.

## Candidate creation sequence

After this convergence PR is merged and reconciled:

```text
verify main is green and unchanged
→ prepare exact 0.3 release request in a dedicated release PR
→ change NEXT_RELEASE.txt to exactly 0.3.0+1.21.1
→ require release-request validation
→ merge only with exact-head protection
→ push on main creates immutable release/tag through existing workflow
→ verify published asset/tag/manifest/JAR identity
→ install exact release asset on clean private test server
→ run required installed acceptance
→ record PASS/FAIL/NOT TESTED honestly
→ reconcile PROJECT_STATE / ROADMAP / CHANGELOG release section
```

No candidate/tag/release should be created from the convergence branch itself.

## Rollback and recovery

Before installed acceptance:

- retain the current known-good server JAR and an offline world backup;
- retain the current official `0.2.0+1.21.1` release as the last installed accepted baseline;
- use a clean test-world/LivingWorld boundary for 0.3 acceptance;
- if the candidate fails startup, persistence, gameplay or AI acceptance, stop the server, restore the pre-candidate world backup and reinstall the known-good release rather than trying to migrate damaged experimental state in place.

GitHub release recovery remains immutable-tag based: it may restore missing release metadata/assets from the already-created tag commit but must never move an existing tag.

## Convergence exit criterion

This plan is complete only when the machine-readable contract, root changelog inventory, persistence/recovery scope, acceptance boundary and exact identity all agree and the frozen PR head passes security, full CI, soak, release dry-run and independent review.

Passing convergence **authorizes candidate preparation as the next development step; it does not itself publish or install 0.3**.
